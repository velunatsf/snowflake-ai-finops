KV Cache Optimization

The largest single lever on multi-turn AI cost, and on latency too

Where you are

This is where the optimization work starts. You met the four token types back in Module 01 and you can now query them from Module 06. Here we go deep on the two cache types, because on conversational workloads they decide whether you pay for the same context once or on every single turn.

This module owns all cache SQL. Module 06 deliberately leaves it out so the queries exist in exactly one place.

Learning Objectives

  • Explain why prompt cache reuse can cut repeated-context spend dramatically
  • Distinguish cache_read_input, cache_write_input, input, and output in practice
  • Connect a high cache-read share to both lower credits and faster multi-turn responses
  • Compute a weekly cache hit rate for CoCo, CoWork, and Cortex Agents
  • Pick the right CoCo view for a KPI without double counting
  • Name the user behaviours that destroy cache reuse
A

Why KV / Prompt Cache Matters

Cost + performance lever (not a daily quota)

In multi-turn CoCo, CoWork, Agents, and REST sessions, most of the prompt is often unchanged history, system instructions, or attached docs. Without caching, every turn re-processes and re-bills that context as fresh input. With prompt (KV) caching, reused context is billed as cache_read_input at a reduced rate. High cache-hit workloads can cut AI spend dramatically (commonly cited toward ~90% on the repeated-context portion). Validate exact rates in the Credit Consumption Table and Snowflake AI pricing.

Cost impact

  • Pay full rate once to write context into cache (cache_write_input)
  • Pay reduced rate to read it on later turns (cache_read_input)
  • Only new tokens each turn bill as standard input
  • FinOps KPI: rising cache-read share with flat/falling total credits

Performance impact

  • Cached KV state avoids re-prefill of the same long context
  • Later turns stay responsive as the thread grows (less redundant compute)
  • Context ring (e.g. 50k / 256k) is session window fill, not a day/month limit
  • Use /compact when the window is full but you need to continue the same thread
Context usage vs spend limits

A UI reading "context usage 20% (~50.1k / 256k Tokens)" measures how full this conversation's model window is. Daily and monthly CoCo limits and AI feature budgets are separate controls, covered in Module 08.

B

Four Token Types to Meter

Snowflake exposes cache telemetry in TOKENS_GRANULAR and CREDITS_GRANULAR on agentic usage views:

  • SNOWFLAKE_COCO_USAGE_HISTORY - unified CoCo (CLI + Desktop + Snowsight); preferred for account-wide CoCo KPIs
  • CORTEX_CODE_CLI_USAGE_HISTORY - CoCo CLI only (see also CORTEX_CODE_DESKTOP_USAGE_HISTORY, CORTEX_CODE_SNOWSIGHT_USAGE_HISTORY)
  • SNOWFLAKE_COWORK_USAGE_HISTORY (org) / account-usage CoWork view
  • CORTEX_AGENT_USAGE_HISTORY - Cortex Agents (excludes CoWork-originated requests)
Which CoCo view for the weekly cache KPI?

Default: use SNOWFLAKE_COCO_USAGE_HISTORY. It covers all CoCo interfaces and includes INTERFACE (cli / desktop / snowsight) so you can roll up or slice without double-counting.

Drill-down only: use CORTEX_CODE_CLI_USAGE_HISTORY when you need CLI-only attribution. Do not sum CLI + Desktop + Snowsight interface views with the unified CoCo view - they overlap.

Metric Meaning FinOps signal
cache_read_input Cached context tokens retrieved and reused on later turns - typically billed at a reduced rate vs standard input High share = healthy reuse; primary savings lever
cache_write_input Initial context tokens processed and written into the cache on the first turn (or when cache is refreshed) Pay once to seed the cache; expect on turn 1
input New, non-cached input tokens processed for the first time this turn Should stay small vs cache reads in long sessions
output Tokens generated by the model in the response Often highest $/token - keep answers concise

Healthy session shape

  1. Turn 1: mostly cache_write_input + some input + output
  2. Turn 2+: growing cache_read_input, small new input, output as needed
  3. Target: cache_read_input >> input for the same conversation

Practices that unlock savings

  • Keep system prompts / large docs stable across turns
  • Continue a session instead of restarting for the same context
  • Avoid rewriting the entire prompt each turn (destroys cache hits)
  • Watch TTL - unused cache entries expire
C

Weekly Cache KPI Queries

These three queries are the canonical cache KPIs for the workshop. They are not repeated in Module 06. The runnable file is training/sql/07-kv-cache.sql, and the general usage and attribution queries they complement are in Module 06.

CoCo (unified) + CoWork + Agents cache hit rate

FinOps KPI
SQL 
-- 1) CoCo ALL interfaces (preferred account-wide CoCo KPI)
-- Docs: https://docs.snowflake.com/en/sql-reference/account-usage/snowflake_coco_usage_history
-- TOKENS_GRANULAR is OBJECT keyed by model. Optional: GROUP BY INTERFACE.
SELECT
    h.INTERFACE,
    f.key                                               AS model_name,
    SUM(COALESCE(f.value:input::NUMBER, 0))             AS input_tokens,
    SUM(COALESCE(f.value:cache_read_input::NUMBER, 0))  AS cache_read_tokens,
    SUM(COALESCE(f.value:cache_write_input::NUMBER, 0)) AS cache_write_tokens,
    SUM(COALESCE(f.value:output::NUMBER, 0))            AS output_tokens,
    ROUND(
      100.0 * SUM(COALESCE(f.value:cache_read_input::NUMBER, 0))
      / NULLIF(
          SUM(COALESCE(f.value:input::NUMBER, 0)
            + COALESCE(f.value:cache_read_input::NUMBER, 0)
            + COALESCE(f.value:cache_write_input::NUMBER, 0)), 0),
      1)                                                AS cache_read_pct_of_prompt,
    SUM(h.TOKEN_CREDITS)                                AS total_credits
FROM SNOWFLAKE.ACCOUNT_USAGE.SNOWFLAKE_COCO_USAGE_HISTORY h,
     LATERAL FLATTEN(input => h.TOKENS_GRANULAR) f
WHERE h.USAGE_TIME >= DATEADD('day', -7, CURRENT_TIMESTAMP())
GROUP BY 1, 2
ORDER BY total_credits DESC;

-- CLI-only drill-down (do NOT also add into the unified CoCo rollup above)
-- Docs: https://docs.snowflake.com/en/sql-reference/account-usage/cortex_code_cli_usage_history
-- FROM SNOWFLAKE.ACCOUNT_USAGE.CORTEX_CODE_CLI_USAGE_HISTORY h, ...

-- 2) CoWork - nested ARRAY (request -> service -> model); org account
-- Docs: https://docs.snowflake.com/en/sql-reference/organization-usage/snowflake_cowork_usage_history
-- Account: https://docs.snowflake.com/en/sql-reference/account-usage/snowflake_cowork_usage_history_view
SELECT
    svc.key                                               AS service_type,
    mdl.key                                               AS model_name,
    SUM(COALESCE(mdl.value:input::NUMBER, 0))             AS input_tokens,
    SUM(COALESCE(mdl.value:cache_read_input::NUMBER, 0))  AS cache_read_tokens,
    SUM(COALESCE(mdl.value:cache_write_input::NUMBER, 0)) AS cache_write_tokens,
    SUM(COALESCE(mdl.value:output::NUMBER, 0))            AS output_tokens,
    ROUND(
      100.0 * SUM(COALESCE(mdl.value:cache_read_input::NUMBER, 0))
      / NULLIF(
          SUM(COALESCE(mdl.value:input::NUMBER, 0)
            + COALESCE(mdl.value:cache_read_input::NUMBER, 0)
            + COALESCE(mdl.value:cache_write_input::NUMBER, 0)), 0),
      1)                                                  AS cache_read_pct_of_prompt,
    SUM(h.TOKEN_CREDITS)                                  AS total_credits
FROM SNOWFLAKE.ORGANIZATION_USAGE.SNOWFLAKE_COWORK_USAGE_HISTORY h,
     LATERAL FLATTEN(input => h.TOKENS_GRANULAR) tg,
     LATERAL FLATTEN(input => tg.value) req,
     LATERAL FLATTEN(input => req.value) svc,
     LATERAL FLATTEN(input => svc.value) mdl
WHERE h.START_TIME >= DATEADD('day', -7, CURRENT_TIMESTAMP())
  AND svc.key <> 'start_time'
  AND TYPEOF(mdl.value) = 'OBJECT'
GROUP BY 1, 2
ORDER BY total_credits DESC;

-- 3) Cortex Agents - same nested ARRAY shape as CoWork
-- Docs: https://docs.snowflake.com/en/sql-reference/account-usage/cortex_agent_usage_history
-- Note: CoWork-originated agent traffic is in SNOWFLAKE_COWORK_USAGE_HISTORY, not here.
SELECT
    h.AGENT_NAME,
    svc.key                                               AS service_type,
    mdl.key                                               AS model_name,
    SUM(COALESCE(mdl.value:input::NUMBER, 0))             AS input_tokens,
    SUM(COALESCE(mdl.value:cache_read_input::NUMBER, 0))  AS cache_read_tokens,
    SUM(COALESCE(mdl.value:cache_write_input::NUMBER, 0)) AS cache_write_tokens,
    SUM(COALESCE(mdl.value:output::NUMBER, 0))            AS output_tokens,
    ROUND(
      100.0 * SUM(COALESCE(mdl.value:cache_read_input::NUMBER, 0))
      / NULLIF(
          SUM(COALESCE(mdl.value:input::NUMBER, 0)
            + COALESCE(mdl.value:cache_read_input::NUMBER, 0)
            + COALESCE(mdl.value:cache_write_input::NUMBER, 0)), 0),
      1)                                                  AS cache_read_pct_of_prompt,
    SUM(h.TOKEN_CREDITS)                                  AS total_credits
FROM SNOWFLAKE.ACCOUNT_USAGE.CORTEX_AGENT_USAGE_HISTORY h,
     LATERAL FLATTEN(input => h.TOKENS_GRANULAR) tg,
     LATERAL FLATTEN(input => tg.value) req,
     LATERAL FLATTEN(input => req.value) svc,
     LATERAL FLATTEN(input => svc.value) mdl
WHERE h.START_TIME >= DATEADD('day', -7, CURRENT_TIMESTAMP())
  AND svc.key <> 'start_time'
  AND TYPEOF(mdl.value) = 'OBJECT'
GROUP BY 1, 2, 3
ORDER BY total_credits DESC;
D

Turning Cache Into a Standing Practice

A cache hit rate is only useful if somebody looks at it on a schedule and knows what to do when it drops. Here is the operating routine.

Weekly review

  1. Run the three queries in Section C and record cache_read_pct_of_prompt per surface.
  2. Compare against last week. A falling ratio with rising credits is the signal to investigate.
  3. Check whether the drop is concentrated in one team, one interface, or one agent.

What to do about a low ratio

  • Coach users to continue a thread rather than starting fresh for the same context.
  • Stabilize system prompts and attached documents so they stay byte-identical across turns.
  • For agents, stop rebuilding the full prompt programmatically on every step.
  • Where the window genuinely fills, use /compact instead of restarting.
Where cache fits with the other controls

Cache optimization reduces what a given workload costs. It does not stop a workload from running away, so it is not a substitute for a spending limit. Pair it with the tag-based AI feature budgets and per-user CoCo limits you build next in Module 08, and put the ratio on the dashboard you build in Module 09.

Knowledge Check

Q1: What does a high cache_read_input share mean for cost?

Most conversation context is reused from the prompt cache and billed at a reduced rate instead of as full input. That is the primary lever behind large (up to ~90% on repeated-context) savings in multi-turn CoCo / CoWork / Agent sessions.

Q2: Is "context usage 20% (50k / 256k)" a monthly spend limit?

No. It is the current conversation's model context window fill. Spend limits are AI Credits, CoCo daily limits, and tag-based AI feature budgets.

Q3: Name one practice that destroys cache savings.

Restarting a new session for the same large context, or rewriting the full system prompt / docs every turn so prior cache entries cannot hit.

Q4: For an account-wide CoCo cache KPI, which view should you use?

SNOWFLAKE_COCO_USAGE_HISTORY (all interfaces; slice by INTERFACE if needed). Use CORTEX_CODE_CLI_USAGE_HISTORY only for CLI-only drill-down - do not double-count with the unified view.

Q5: Your cache hit rate is healthy at 85 percent, but total AI credits doubled this month. Has cache optimization failed?

No. A high hit rate means each conversation is efficient; it says nothing about how many conversations are happening. Rising volume with a healthy ratio usually means adoption grew, which is a budgeting question rather than an optimization one. Confirm the volume story with the trend queries in Module 06, then set limits in Module 08.
